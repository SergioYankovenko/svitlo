# Моніторинг та відновлення «Світло»

Локальні Netdata і host evidence працюють на приватному VPS. Вони збирають CPU/RAM/диск, стан PostgreSQL/WAL, вік копії та стан релізу. Адмінка читає останні спостереження; після трьох хвилин без даних стан стає невідомим. Сирі логи, секрети й адреси користувачів у панель не потрапляють.

Для незалежного контролю розгорнути [Uptime Kuma](https://github.com/louislam/uptime-kuma) на іншому хості з власним живленням і мережею, закріпити перевірений digest і змонтувати окремий том даних. Приватний endpoint перевіряти через TLS, із секретом лише в налаштуваннях монітора. Адмінку, Netdata, PostgreSQL і внутрішні метрики залишити на закритих інтерфейсах. Моніторинг має працювати, коли основний ПК вимкнений.

| Сигнал | Що перевіряти | Коли сповіщати |
|---|---|---|
| API /healthz | HTTPS, HTTP 200, очікуване JSON поле стану | Інтервал 60 с, після двох поспіль невдалих спроб |
| API /readyz | HTTPS, HTTP 200, стан ready і підтримуваний реліз | Інтервал 60 с, після двох поспіль невдалих спроб |
| Джерела графіків | Вік останнього підтвердженого графіка за джерелом і дата, на яку він поширюється | Окреме сповіщення після порога конкретного джерела |
| Резервне відновлення | Вік останньої звіреної копії й архівації WAL | Відповідно до заявленого RPO; без зовнішнього WAL цей критерій відкритий |

Узгодити приватного отримувача перед увімкненням доставки. У тесті імітувати відмову окремого тестового endpoint, перевірити повідомлення про відмову та відновлення й зафіксувати час. Це не вимагає вимикати продуктивний API. Зовнішній тест охоплює також відмову самого VPS.

Для незалежного відновлення потрібні зовнішній репозиторій WAL, окремий вузол із тією ж сумісною версією PostgreSQL, доступ до зашифрованого backup і перевірене офлайн зберігання пароля переносного ключа. На відновленій БД окремо звірити контрольну точку, відсутність запису після неї, ролі, зв’язки датчиків, epochs, квитанції та історію. Локальне відновлення і OneDrive readback перевіряють інші частини цього процесу.

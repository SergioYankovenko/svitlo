# PWA 1.1.5 — sync і сумісне розгортання

Статус: локальна реалізація, production не змінено. Авторизація чинного svitlo-api залишається; owner лише з перевіреного сеансу, поле owner у тілі не використовується.

## POST sync

```json
{"action":"sync","id":"optional-owned-profile-id","reason":"auto|manual|push|rollover","subscription":{"endpoint":"https://…","keys":{"p256dh":"…","auth":"…"}}}
```

id відсутній — перший власний профіль або порожній список. Невідомий/чужий/видалений явний id — 404. subscription необов’язкова; використовується лише після зміни або добової перевірки реєстрації, перевіряються чинні allowlist/ключі/VAPID. Прив’язка лишається до активної адреси.

Відповідь: profiles (власні, без account), active, vapid, pushReady, weather, weatherKey, subscription (true тільки після збереження), errors за частинами, serverTime. Погода та реєстрація підписки не блокують профілі. Графік/погода зберігають фактичні timestamps. Жодного внутрішнього HTTP виклику старих Edge actions: sync виконує сервіс напряму.

## Кеш і відновлення

- svitlo-sync-v1 прив’язаний до owner; звичайна перевірка через 60 хв, лише видима сторінка/повернення у вікно. Приховані вкладки не опитуються.
- Повторне відкриття зі свіжими даними — 0 Edge. Час свіжості обмежений timestamp джерела, а не часом повторного читання. Часткова відповідь — повторна спроба не раніше 5 хв, старі timestamps не змінюються.
- Manual / push / Kyiv midnight обходять клієнтську затримку; сервер лишає хвилинний cooldown і наявний provider cache/leases/CAS/rate limits. Нормальна серверна перевірка — наступний due/60 хв.
- navigator.locks узгоджує вкладки; fallback — локальний lease з перевіркою токена. Epoch/generation не дають пізнім відповідям перезаписати мутацію або повернути видалені дані. Зміна owner очищає видимі приватні дані.
- Fingerprint: owner envelope + profile + endpoint + keys + VAPID. Успіх запам’ятовується тільки після ack. Незмінна підписка перевіряється щодоби в sync. VAPID ремонтується лише за вже наданого дозволу, без автоматичного permission prompt.
- Погода за точним ключем department/cityId/назва з типом, 1 год клієнт/сервер. Місто та село не об’єднуються. Спільний серверний кеш використовує чинний service-only source cache без нової таблиці.
- dictionary cache v1: kind+parent, 24 год; точні IDs/назви/будинки, тільки успішні масиви. Помилковий застарілий вибір скидає залежні поля й один раз примусово завантажує відповідну гілку, без нескінченних повторів.
- SW зберігає інвалідацію профілю у svitlo-events-v1 поза app-shell cache. Вікна отримують postMessage; закриті/офлайн прочитають маркер при відкритті. Мережевого фонового refresh на кожен push немає. Обмежена історія tag усуває дублікати. Ack використовує маркер на початок sync: новий push під час запиту не губиться.

## Канали

publication / change незалежні, успадковують schedule. До першого незалежного вибору старий schedule master працює як раніше; після нього legacy-запис не затирає незалежні значення. Внутрішня _scheduleSplit мітка забезпечує це також для старої API-версії через SQL trigger. Нові записи — атомарний patch під owner/id, не заміна всього об’єкта.

reminder / restoration / emergency / lead збережені. address_emergency використовує emergency preference. Перша публікація визначається ревізіями плану, включно зі сьогодні; початкова історія не розсилається. Старі schedule доставки без точного subtype консервативно потребують обох увімкнених каналів до їх завершення. Нові версії PWA — лише чинне внутрішнє SW-повідомлення, без нового системного каналу.

Обласні попередження — тільки стрічка. Заборона regional event_key діє при SQL enqueue; старі регіональні записи відсіюються delivery_valid за збереженою ознакою region у повідомленні. Адресні аварії вимагають свіжого успішного адресного джерела. Фільтрація налаштувань, owner/subscription/generation перевіряється повторно перед доставкою.

## Порядок майбутнього розгортання

1. Окреме доручення на production. Застосувати локальну міграцію 20261028005221_pwa_sync_notification_channels.sql.
2. Розгорнути сумісні API та jobs разом: sync, нові канали/шаблони; старі actions зберігаються. Не викликати jobs вручну для масового тесту.
3. Перевірити контрольний тест власного пристрою лише за окремим дорученням; потім публікувати PWA/dist/app з повним hashed shell. Попередні вкладки завершують стару версію штатно.
4. Відкат UI до 1.1.4 не потребує видалення нових полів/SQL. Старі actions працюють, незалежні налаштування зберігаються. Не відкочувати міграцію видаленням чужих даних.

Наразі жоден із production-кроків не виконано.
